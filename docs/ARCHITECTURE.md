# Architecture

## Stack

| Area | Choice |
|---|---|
| Language | TypeScript (strict), ESM |
| Runtime | Node 24 LTS (default) |
| Package manager | npm, exact versions only (default) |
| Server HTTP | `node:http` built-in, small route table, SSE for streams |
| Browser UI | Svelte 5 + Vite, plain SPA, no SvelteKit |
| Code viewer | CodeMirror 6 (read-only), `@codemirror/merge` for diffs |
| Parsing | `web-tree-sitter` with WASM grammars for TS, TSX, JS (default; no native build, so `npx` works on Windows) |
| Search | ripgrep via `@vscode/ripgrep` |
| Validation | zod at every boundary (HTTP bodies, LLM output, files read from `.tutor/`, eval cases) (default) |
| Tool protocol | `@modelcontextprotocol/sdk`, stdio server |
| File watching | `node:fs` `watch` with `recursive: true` (default) |
| Source maps | `node:module` `SourceMap` (built in) |
| Format + lint | Biome (default) |
| Types | `tsc --noEmit` + `svelte-check` (TypeScript 6; `svelte-check` does not support 7 yet) |
| Tests | Vitest (default); Playwright for browser e2e from Phase 4 (default) |
| Unused code | Knip (default) |

## Build and run

- Dev and tests run the TypeScript directly: `node src/server/cli.ts`.
- `npm run build` runs `vite build` (to `dist/web`) and `tsc -p tsconfig.build.json` (to `dist/server` and `dist/shared`, leaving out `src/server/evals`, which only runs from the repo). Node won't strip types under `node_modules`, so the published package runs `dist/server/cli.js` (`bin`), and ships only `dist` and `THIRD_PARTY_NOTICES.md`.
- The server finds `dist/web` relative to its own module location, so the same code works from `src/server` and `dist/server`.
- Anything that starts Miyagi again (the MCP server) uses `process.execPath` plus `process.argv[1]`.

## Parts and how they talk

```
Browser (Svelte)                         Node server (one process)
  code viewer + highlights      HTTP+SSE   CodeSource -> folder on disk
  tour player + tour stack   <---------->  filter + redaction + path guard
  push-to-talk / VAD          127.0.0.1    parse cache, repo map, anchors
  Whisper STT, local TTS      + token      tools (plain functions)
  selection chip                           LLMProvider -> stream of events
                                              |
                                              +-- ClaudeHeadless: spawns `claude -p`
                                              |     -> stdio MCP: `askmiyagi mcp <root>` (read-only tools)
                                              +-- ClaudeAPI / GeminiAPI: own agent loop, tools called directly
                                           .tutor/ store
```

- **Browser to server:** JSON over HTTP; `POST /api/ask` answers with a server-sent event stream. The server injects a random per-session token into `index.html` as `<meta name="miyagi-token" content="<64 hex chars>">`, the chosen voice as `<meta name="miyagi-voice" content="browser|elevenlabs|kokoro">`, and the project name as `<meta name="miyagi-project" content="<URI-encoded name>">` (the folder name, or the repository name for a GitHub URL; `projectName` in `src/server/source/project-name.ts`); every `/api/*` request sends it as `x-miyagi-token`. API errors are `{ "error": "<reason>" }`.
- **Server to Claude Code:** `ClaudeHeadless` spawns `claude -p` with stream JSON output, all built-in tools off, `--strict-mcp-config` with only Miyagi's MCP server, `--allowedTools` limited to `mcp__miyagi__*`, user settings and plugins not loaded, and an empty temp working folder. The MCP server is the same binary: `askmiyagi mcp <root>`, plus `--app <folder>` for a monorepo app.
- **Voice is swappable.** The browser speaks through one `Speaker` interface: `browser` (local `speechSynthesis`, default), `elevenlabs` (opt-in; the server calls ElevenLabs through `POST /api/speech` with redacted text, so the key never reaches the page), and `kokoro` (opt-in; the free Kokoro-82M model runs in a Web Worker in the page). Microphone audio never leaves the browser, except speech input (push-to-talk or hands-free, see [ADR 0007](adr/0007-hands-free-speech-to-elevenlabs.md)) with `--voice elevenlabs`, which goes to ElevenLabs speech-to-text through the server; every other voice transcribes with Whisper (`whisper-base.en`) in a Web Worker in the page. Whichever engine transcribes, `withCleanup` (`src/web/cleanup.ts`) then removes filler words and rewrites words that spell a repo symbol, using the names from `GET /api/symbols` (fetched in parallel with the transcription). See [ADR 0002](adr/0002-swappable-voice-with-elevenlabs.md) and [ADR 0003](adr/0003-elevenlabs-speech-to-text-for-the-demo.md).
- **Tour stack is browser state** (playback position), so pause and resume are instant. After a side answer the interrupted tour resumes on its own; after a new topic it waits on the stack until the learner says or presses resume. Each stack entry carries its own `waits` flag, set from the scope of the answer that pushed it, so a side answer never brings back a tour that a new topic set aside.

### Code changes mid-tour

`watchFolder` (`src/server/files/watcher.ts`) runs `fs.watch` on the project root (recursive) and reports the changed paths, with `/` separators, once per burst: changes are debounced 100 ms. A watch that cannot start or stops logs one `miyagi:` line and the app carries on without live updates. Nothing is cached by path (the parse cache is keyed by content hash and the repo map is built on every ask), so there is nothing to invalidate. `createTourWatch` (`src/server/tour-watch.ts`) is told when an ask starts (`start(base?)`, which forgets the old tour and keeps the ask's diff base, so later changes re-resolve old-side anchors against it) and gets each streamed step's anchors and ranges (`addStep`). When a changed path (compared ignoring case and `\`) is the file of any anchor, `changed(paths)` re-resolves every anchor of the tour with `resolveAnchor` and publishes a `ranges` event (one list of ranges per step, as in the `tour` event) and then one `stale` event (`{ file }`) per file where an anchor that had a range can no longer be found. If a newer change or a new ask arrives while it resolves, the older result is dropped. `GET /api/events` (`events-route.ts`, token checked like every `/api` route) sends these as `data: <json>` SSE blocks to every open page; `watchEventSchema` is in `src/shared/events.ts`. In the browser, `watchCode` (`src/web/watch.ts`) reads the stream with the same reader as `ask` (`sse.ts`); `App.svelte` replaces the steps' ranges on `ranges`, moves the highlight to the current segment's new range and reloads the viewer, and on `stale` removes the highlight of that file and shows "Code changed; highlight removed" until the next segment or question.

## Security model

- Bind to `127.0.0.1` only. Reject a `Host` other than `127.0.0.1:<port>` or `localhost:<port>` (403), any `Origin` that isn't the server's own (403), and `/api/*` requests without the session token (401).
- Never execute anything from a repo. Read only. Git is used only for `clone --depth 1` (no submodules, no LFS smudge) and the read-only `diff` (including `diff --no-index` against a snapshot, run by Miyagi and never from model input), `show`, `log`, `fetch`, `rev-parse` and `merge-base`.
- Every path goes through the path guard: resolve, `realpath` (follows symlinks), refuse anything outside the project root, then the shared file filter. Two reads skip the filter but keep the guard: a stack frame's generated `.js` file and its source map, used only to find the original file and line (the original file goes through the filter). Snapshot files are read from `.tutor/private/snapshot/` with a `realpath` check that they stay inside the snapshot, after the path is checked as visible.
- The shared file filter exposes `isVisible(root, relPath): Promise<boolean>`, `isVisibleInDiff(root, relPath)` (the same, but a file deleted from disk is judged by its path alone: the name, `.gitignore` and `.gitattributes` generated rules) and `listVisibleFiles(root): Promise<string[]>`. The list contains sorted root-relative paths, and traversal prunes excluded directories before descending. Filtering applies nested `.gitignore` files and root `.gitattributes` generated markers, and excludes the planned lockfiles, secrets, binaries and oversized files.
- Every byte leaving the machine (tool results, brute-force content, ElevenLabs narration text) passes secret redaction.
- No network tools for the model, ever ("lethal trifecta": remove external communication). File contents are data, never instructions; tool results are wrapped in labelled untrusted blocks.
- PR review drafts comments; it never posts them.

## Data contracts (`src/shared`)

Each contract is a zod schema with its type inferred from it, one file per area (`anchor.ts`, `tour.ts`, `events.ts`, `usage.ts`, `call-log.ts`, `session.ts`, `llm-request.ts`, `tool-result.ts`, `result.ts`, `file.ts`, `diff-base.ts`, `learner.ts`, `path.ts`), and the tool input schemas are in `tool-inputs.ts`. `parseContract(schema, data)` returns a `Result` whose error lists each problem on its own line as `path: message`.

Paths everywhere (tool inputs and results, anchors, selections, routes, events) are relative to the project root with `/` separators. Only the path guard turns them into real paths.

Explain-back: a tour that keeps a check question starts a background `small` call that saves the check concept's `rubric` in `learner.json`. A grade passes at a score of 4 or more: the concept becomes checked (state moves forward only) and its review is due after 1 day; a pass of a review (`review: true` in the request) sets it to reviewed, counts `reviewsDone` and schedules the next review after 3, then 7 days, then none. A fail adds an attempt; the third fail resets `attempts`, gives the model answer and schedules a review after 1 day (`reviewsDone` back to 0). A failed review starts the schedule again at once (`reviewsDone` 0, next review after 1 day), and a retry that then passes keeps that 1-day review. A tour that keeps a question starts that concept's failed attempts again. In a tour without PRIMM the server sets the end question to "Explain <concept> back to me in your own words.". The browser shows the explain-back chip once the end question is reached: in text mode, or when the voice has played the tour to its end. It offers a due review only when no earlier tour waits to resume, and a review that is cleared by a new question is reported as skipped. The request and reply schemas (`explainBackBodySchema`, `gradeSchema`, `explainBackReplySchema`, `dueReviewsSchema`) are in `src/shared/learner.ts`.

### Providers

`LLMProvider` is `ask(request: LLMRequest, signal: AbortSignal): AsyncIterable<ProviderEvent>` (`src/server/llm/provider.ts`); aborting the signal ends the stream. `loadFakeProvider(file)` (`fake-provider.ts`) returns a `Result` holding a provider that replays a recording: one `ProviderEvent` JSON per line, with an optional `delayMs` waited before that event. The hidden CLI flags `--provider fake --recording <file>` load it at startup and exit 1 with the problems (`line <n>: <path>: <message>`) if the recording is bad.

### Ask pipeline

`POST /api/ask` (`src/server/http/ask-route.ts`) validates `{ question, selection?, current?, diff?, intent?, pathConcept? }` (`pathConcept` is added to the prompt as an untrusted `path_concept` block and joins the tour's concepts as an important repo concept whenever the tour has steps, so playing the tour ticks the path item) (`intent` is the shared `intentSchema` in `src/shared/intent.ts`) (`current` is `{ tour, step, segmentIndex }`: the question that produced the tour on screen and the segment being heard; `describePosition` in `src/server/llm/position.ts` adds that step and segment (its anchor resolved against the diff base the earlier ask used, which the conversation keeps with each turn, and old-side code read from that base) (wrapped as an untrusted `tour_position` block, because it is model output) and its highlighted code, read through the path guard and redacted, to the model's question, and sends nothing extra when the tour is no longer in the conversation) (a question of at most 2,000 characters; 400 on a bad body or one over 100 KB), answers 409 while another ask runs, and streams `AskEvent`s as `data: <json>` SSE blocks; a closed connection aborts the provider. `createAskHandler` returns `{ handle, played, interrupt }`; `serve.ts` routes `POST /api/played` to `played`, which marks the played tour's concepts explained in the learner record. The browser sends it (`postPlayed`, `src/web/played.ts`) when a tour that arrived has finished playing, or, with the voice off, turned off or failed, as soon as the tour is shown; an ask that ended without a tour sends nothing. When an ask ends with `done`, `askEvents` starts `markSeen` for the tour's concepts without waiting for it, so the stream ends and the next ask can start before `learner.json` is written; the record's write queue keeps the updates in order. The queue skips an update when `learner.json` exists but cannot be read (a locked file, no permission), logs it, and leaves the file alone; a missing or invalid file starts a new record (an invalid one is moved to `learner.json.corrupt`). `POST /api/interrupt` (routed in `serve.ts`) calls `interrupt()`, which aborts the running ask and waits until it has finished, so the next ask never meets a 409. An aborted ask that had sent steps is stored in the conversation as a partial turn (the question and those steps), so a side question about it still finds its position. `askEvents` (`src/server/llm/ask.ts`) yields the `ack` phrase (rotating through `ackPhrases` in `src/shared/phrases.ts`) before anything else, then checks the selection with `checkSelection` (`selection.ts`: the file is visible, the lines exist and contain the text; on a mismatch it sends a `progress` note and drops the selection), builds the request with `buildRequest` (a valid selection is added to the question as an untrusted block). A question with two or more stack frames (lines like `at fn (file:line:col)`) is parsed by `parseStackTrace` (`src/server/llm/stack-trace.ts`), anchored by `anchorStackTrace` and the model gets `formatStackTrace` instead of the raw text, with `stackTraceRules` added to the system prompt (steps run symptom, then trace back to where the bad value was created, then fix options) (`anchorFrame` in `src/server/code/frame-anchor.ts` finds each frame's project file by its longest path suffix that exists, follows a `sourceMappingURL` that names a `.map` file (a regular file of at most 10 MB, like the generated script; an invalid map is logged without its contents) with `node:module` `SourceMap`, and checks with tree-sitter that the named function encloses the line; maps are read through the path guard without the file filter, only to look up the original file and line, and are never sent to the model; the original file goes through the guard and the filter; a frame whose function is not at that line carries a `[warning: ...]` note for the model and a `progress` event `Warning: ...` for the learner): the learner's other lines, the app frames as `at fn (file:line:col)` and each run of `node:` and `node_modules` frames (and frames with no file position, such as `<anonymous>`) as one `... N frames from Node or node_modules collapsed` line, all inside an untrusted `stack_trace` block. With a `diff` in the body it first builds the diff message (before `buildRequest`, after the selection check) with `buildDiffContext` (`src/server/llm/diff-context.ts`: the diff from `diffAgainstBase`, at most 200 lines for every base, with the learner's `why` and, for the `branch` base only, the messages of the commits in `<default>..HEAD` from `branchCommitMessages` (at most 50, each cut at 2,000 characters), each in its own untrusted block (`why`, `commit_messages`, `diff`) and the whole message redacted; with no why it tells the model nobody said why, so it starts each claim about the intent with "it looks like"). It reads the whole diff, not the 200 lines the model sees, and `findRisks` (`src/server/llm/diff-risks.ts`) lists in code, per file, each removed guard (an `if`, `elif` or `unless` line that returns, throws, raises, continues or breaks on the same or the next removed line), removed `throw` or `raise`, removed test (`it`, `test` or `describe` calls, `def test_`, `func Test`), and added or removed `try`, `catch`, `finally`, `except` or `rescue` line; a line that appears on both sides of the file (re-indented or moved) and a comment line are ignored. `findCoveringTests` lists each changed test file (by name or folder) with the changed source files it imports, resolved by `resolveRelativeImports` (`src/server/code/repo-map.ts`, the same resolution the repo map counts imports with) and read through the path guard. Both go into the message as untrusted blocks (`risk_flags`, `covering_tests`), or "No removed guards…" when there are no risks. A diff that is empty or can't be read (no snapshot, no default branch, not a git repository) ends the ask with an `error` event before the model is called. Otherwise the message is added to the question and `diffRules` (steps in the order problem, intent, how; trivial changes in one step; changed tests as proof of intent; a last "Things to verify" step only when risks are listed; anchors on the new code by default and `side: "old"` on the anchor of removed or replaced code) to the system prompt, for that ask only (the conversation keeps just the short question), turns `tool_call` events into `progress` lines, resolves every step's anchors against the ask's diff base, when it has one (`null` when unresolvable), then stores the turn in the `conversation` it is given when the tour has at least one step or a reply and sends `tour` and `done`. `createConversation({ contextTokens })` (`src/server/llm/conversation.ts`) keeps every turn of the session as the redacted question, a redacted one-line record (`Tour:` with the step titles and check question, or `Replied:` with the reply), the redacted whole answer (the step JSON lines and check question, or the reply) and, for the API providers, the agent messages from the `done` event (user and assistant text redacted). `render()` is the text for ClaudeHeadless: the last 3 turns as question plus whole answer, older turns as question plus record, each wrapped as an untrusted block (`tour_answer`, `tour_record`) because it is model output. `messages(contextCharacters)` is the history for the API providers; when the repo context plus all retained messages, estimated as characters divided by 4, pass 50% of `contextTokens` (the hidden `--context-tokens <n>` flag, default 200,000), every tool result of a turn older than the last 3 becomes `[<tool> result removed]` in one batch. `askEvents` builds the request with `buildRequest`, passing `conversation.size()` (the longer of the text rendering and the messages, in characters) so the brute-force check is made again before every ask on the repo size plus the conversation size against the brute-force budget (`--brute-force-tokens`); a long session can therefore move from brute-force to agentic mode. It then adds `conversation: render()` and `history: messages(context length)`. In answer mode (the profile's `mode`, or the `mode` option the evals pass) `askEvents` adds `answerModeRules` (`prompt.ts`) to the system prompt and drops any `checkQuestion` the model still returns, so neither the tour nor the conversation keeps it; the panel header's Teach mode switch saves the mode with `PUT /api/profile` (disabled until a profile exists and while its questions are asked). In the browser, `pickSelection` (`src/web/selection.ts`) turns the editor selection on mouse-up into a `Selection` (a click on a symbol selects its line with the identifier as `text`); `App.svelte` shows it as a removable chip and sends it with the next question only. An `error` provider event, a thrown provider failure, or a reply that is not plain speech (over 600 characters, or a line starting with `{`, `[` or a code fence) ends the ask with an `error` event and no `tour`. `--provider claude-headless|claude-api|gemini` (default `claude-headless`, plus the hidden `fake`) is turned into a provider at startup by `chooseProvider` (`choose-provider.ts`): `claude-api` needs `ANTHROPIC_API_KEY` and `gemini` needs `GEMINI_API_KEY` (`--model` overrides their default model), `claude-headless` needs `claude` on the PATH (`findClaude`); otherwise the server prints `Set <KEY> to use --provider <name>` or `Claude Code was not found…` and exits 1 before opening the source. `claudeHeadless` (`claude-headless.ts`) is the default provider; `--brute-force-tokens <n>` sets the brute-force threshold and `--context-tokens <n>` the conversation context budget (positive integers, validated with zod). `--model <name>` (letters, digits, `.`, `_` and `-`, not starting with `.` or `-`) is passed to `claude -p --model` or to the API provider; without it Claude Code or the provider uses its default model. `--voice browser|elevenlabs|kokoro` (default `browser`) and `--voice-id <id>` pick the voice; `elevenlabs` exits 1 without `ELEVENLABS_API_KEY`, and the default voice id is the premade ElevenLabs voice `JBFqnCBsd6RMkjVDRZzb` (`defaultVoiceId` in `src/server/cli-args.ts`). In the browser, `src/web/speaker.ts` holds the `Speaker` interface, `speak(text, signal, onStart?): Promise<void>` (`onStart` is called once when the audio actually starts, which is when the page highlights the segment; the promise resolves when the audio ends; aborting stops it at once), with `browserSpeaker` (local `speechSynthesis` voices only) and `elevenLabsSpeaker` (posts to `/api/speech`, falls back to the browser voice). `src/web/playback.ts` plays a tour through any `Speaker`: it speaks segments in order, reports each one as its audio starts (the page highlights it then), moves the viewer to a segment's file 200 ms before that segment is spoken when it differs from the previous segment's file (the `onLead` hook; the page shows the new file and highlight but only changes the playing segment at `onStart`), and is stopped or restarted from any segment; `stop()` returns the segment it interrupted (even one whose audio had not started yet), which Resume plays again from its start; after the last segment the `closing` hook may return the tour's check question, which is spoken before playback ends (`play(undefined)` speaks only that, for a tour whose segments were already played); a narration part that fails to play is skipped, and only a missing local voice puts the page in text mode with a segment selected. The page starts playing at the first `step` event and, if playback has caught up with the steps received so far, continues when the next step arrives (unless the user paused). `src/web/announcer.ts` speaks the `ack` phrase (neutral phrases such as "Okay, let me see.") and at most the first two file or symbol `progress` lines, phrased by `spokenProgress` like a person ("Let me look at upload.", then "Now ask route."; searches are not spoken and the server sends each progress line once per ask), through the same `Speaker` one line at a time; a failed note is skipped; a line still waiting when the first `step` arrives is dropped, later progress lines are not spoken, and playback waits for a line already being spoken. With `--voice elevenlabs`, `chooseSpeaker` preloads the `ackPhrases` through `elevenLabsSpeaker.preload` once at page load, so they play from memory; once a segment starts playing, `playback.ts` calls the speaker's optional `prefetch` with the next segment's text (or the closing line), and `elevenLabsSpeaker` fetches that audio early, keeps only the latest prefetched sentence, uses it once, and cancels it when a different text is spoken or prefetched; progress lines are sent to ElevenLabs too, after redaction. With `--voice kokoro`, `chooseSpeaker` starts `src/web/kokoro-worker.ts`. The worker loads `onnx-community/Kokoro-82M-v1.0-ONNX` with `kokoro-js` (WebGPU with `fp32` when the browser has a GPU adapter, otherwise wasm with `q8`) and speaks with the voice `af_heart`, one sentence at a time (`speakSentences` in `src/web/kokoro-speech.ts` splits the text with kokoro-js's `TextSplitterStream` and joins the audio, so long text is not cut off at the model's input limit). Both model workers (Kokoro and Whisper) are built on `serveModel` (`src/web/model-worker.ts`): it picks the device, answers `{ type: "run", id, input }` requests one at a time, skips a request cancelled with `{ type: "cancel", id }` while it waits and aborts the signal of one that is running, and replies with `{ type: "result", id, result }` (Kokoro's WAV `Blob`) or `{ type: "error", id, message }`, and reports `progress` (the summed download of all model files, in steps of 10%), `ready` or `failed` (the `ModelReply` type in `src/web/model-download.ts`). On the page, `createModelEngine` matches each reply to its request, sends a cancel when a request's signal aborts, and on a failed load or a worker crash terminates the worker, fails the load and every waiting request, and reports `stopped` so later requests fail at once. `kokoroSpeaker` speaks with the browser voice until the model is ready; with no browser voice it waits for the model instead, and only a failed load then puts the page in text mode. The page shows "Downloading the local voice: <n>%" and then "Local voice ready". From then on it plays the worker's WAV audio, with the same preload (the `ackPhrases`, made as soon as the model is ready), prefetch and fallback as `elevenLabsSpeaker` (both are built on `audioSpeaker` in `speaker.ts`). A failed load says "Local voice failed to load, using the browser voice" and stays on the browser voice. The ONNX runtime's `.wasm` is bundled into `dist/web/assets` (the worker clears the jsDelivr `wasmPaths` that transformers sets by default), so only the model files and the voice file come from Hugging Face, and the browser's Cache API keeps them after the first download (see [ADR 0006](adr/0006-kokoro-local-voice.md)). Tests can set `window.__MIYAGI_SPEAKER__` before load to replace the speaker. `POST /api/speech` (`src/server/http/speech-route.ts`) validates `{ text }` (1 to 2,000 characters), answers 404 unless the voice is `elevenlabs`, redacts the text, calls ElevenLabs text-to-speech (`eleven_flash_v2_5`, `mp3_44100_128`) with the key from the environment, and returns `audio/mpeg`; ElevenLabs errors and empty audio become 502 `Voice service failed: <status>`; a network error, a cut-off body or no answer within 15 s becomes 502 `Voice service failed: unreachable`. Audio is cached in memory by SHA-256 of voice id and text. `POST /api/transcribe` (`src/server/http/transcribe-route.ts`) answers 404 unless the voice is `elevenlabs`, 415 unless the content type is `audio/webm`, `audio/ogg` or `audio/wav`, 400 for an empty body and 413 over 10 MB, sends the recording to ElevenLabs speech-to-text (`scribe_v2`, audio event tags off) with `fetch` and `FormData`, and returns `{ text }` (trimmed, shared `transcriptSchema` in `src/shared/transcript.ts`); an ElevenLabs error becomes 502 `Speech-to-text failed: <status>`, and a network error, an unreadable answer or no answer within 30 s becomes 502 `Speech-to-text failed: unreachable`. In the browser, holding the microphone button or Space (outside text fields and other controls) calls `startRecording` (`src/web/recorder.ts`: `getUserMedia` with echo cancellation and noise suppression, `MediaRecorder` recording `audio/webm`, or `audio/ogg` where webm is unsupported), pauses narration (the button stays enabled while an answer streams), and on release (or when the window loses focus) `transcribe` (`src/web/transcribe.ts`) turns the recording into text; a release before the microphone opened sends nothing and says "Hold the button while you speak", and a new recording cannot start while the last one is transcribing; `chooseTranscriber` (`src/web/transcribe.ts`) picks the transcriber: with `--voice elevenlabs` it posts the recording to `POST /api/transcribe`, with every other voice local Whisper transcribes it in the browser (`createLocalTranscriber` in `src/web/whisper.ts` starts `whisper-worker.ts` on the first recording, shows "Downloading the speech model: <n>%", decodes the recording to 16 kHz mono with `decodeRecording`, and starts a fresh worker on the next recording after a failed load or a worker crash; the worker loads `Xenova/whisper-base.en` and transcribes in 30 s chunks), and `withCleanup` (`src/web/cleanup.ts`) cleans every transcript (tests set `window.__MIYAGI_TRANSCRIBER__` before load to replace the transcriber) before `App.svelte` handles it: when a tour is on screen (or, for resume, a tour waits on the stack) and the whole utterance is one local command, `matchCommand` (`src/web/commands.ts`: go back, repeat, skip, slower, faster, pause, resume, ignoring case and the punctuation around it) runs it with no LLM call (go back and skip do nothing at the first and last segment; slower and faster step the speed by 0.25 within 0.5–2.0 through the optional `Speaker.setRate`, which sets the utterance `rate` of the browser voice and the `playbackRate` of the audio element for ElevenLabs and Kokoro, including audio already playing; when push-to-talk or hands-free paused the narration, slower, faster and a go back or skip with nowhere to go resume it); anything else is sent at once as a question (when an answer is still streaming, `App.svelte` first aborts that ask's `fetch`, ignores its late events, calls `POST /api/interrupt` through `interruptAsk` in `src/web/ask.ts` and pushes the steps received so far onto `earlierTours` as a partial tour, at the interrupted segment or, when narration had caught up with the stream, at the last segment heard), or the page shows "Didn't catch that" for an empty transcript. The Hands-free toggle beside the microphone button (off by default, not remembered) starts `startDetector` (`src/web/hands-free.ts`), which loads `MicVAD` from `@ricky0123/vad-web` on first use with the Silero `v5` model, `minSpeechMs` 300 and `redemptionMs` 650, opening the microphone with echo cancellation through `openMicrophone` (`recorder.ts`); the model, the audio worklet and the ONNX runtime (`ort-wasm-simd-threaded.wasm` and `.mjs`) are copied into `dist/web/vad/` by the `voiceDetectorFiles` plugin in `vite.config.ts` and loaded from `/vad/` (tests set `window.__MIYAGI_DETECTOR__` to replace the detector). In `talk.svelte.ts`, detected sound lowers the narration to 20% through the optional `Speaker.setVolume` (the audio element's `volume` for ElevenLabs and Kokoro; the browser voice has none, so its volume stays as it is); a misfire restores it; at the end of speech the audio is encoded as 16 kHz WAV (`encodeWav`) and goes through the same transcriber as push-to-talk (`POST /api/transcribe` with `--voice elevenlabs`, see [ADR 0007](adr/0007-hands-free-speech-to-elevenlabs.md)); a non-empty transcript pauses playback, restores the volume and is handled like a push-to-talk transcript, an empty one only restores the volume. Speech that overlaps a push-to-talk recording is ignored, so it is never asked twice. The page says "Listening hands-free" while the detector runs. The page is a two-pane app: `Viewer.svelte` (dark CodeMirror theme; syntax colours come from `defaultHighlightStyle` remapped to dark colours) with the file path header fills the left pane, or `App.svelte` shows the project name and three suggested questions before the first question; `Conversation.svelte` is the right panel (about 400 px, stacked above the code below 900 px) with the question bubbles, the tutor's note lines, the `Player.svelte` tour card and the check question as a tutor bubble, and a composer pinned at the bottom (Enter sends, Shift+Enter adds a line); `VoicePill.svelte` floats at the bottom centre of the code pane while a tour is on screen with voice on (with voice off, `Player.svelte` shows Previous, Next and Voice itself). Sending a question clears the question box. A question asked while a tour is playing or paused with voice on pushes that tour and its interrupted segment onto `earlierTours` in `App.svelte`; once the answer has been spoken (or produced nothing), unless it ended with a check question waiting for the learner, the page says "Now, back to where we were.", adds a "Back to where we were" line to the conversation, and replays the earlier tour from the start of the interrupted segment; turning the voice off or text mode empties `earlierTours`. If no part of a tour could be spoken, playback ends with the error and the page switches to text mode. Space starts push-to-talk on the button the learner last clicked; after Tab, Space presses buttons as usual. Server errors are written to stderr as `miyagi: …` by `logError` (`src/server/log.ts`, redacted and with control characters removed): every error response with its status (ElevenLabs failures with ElevenLabs' reason, the key removed), every failed ask with its detail, and every anchor that could not be resolved. On SIGINT or SIGTERM the server closes all connections, which aborts a running ask and kills Claude Code's process tree.

### Eval runner

`npm run eval -- --suite <name> --provider <fake|claude-headless> --runs <n> [--mode teach|answer]` (`src/server/evals/cli.ts`, `eval-command.ts`) loads `evals/<name>.json`, runs each case `n` times (default 3) through `askEvents` on a temp copy of the repo (`runner.ts`), and prints a score table (`score-table.ts`) after saving `evals/results/<start time with : replaced by ->.json`. Each run asks `Intent: <intent>` followed by the question, with a fresh conversation, in the given mode (default `teach`); in `answer` mode the `questionsOnlyAtEnd` check also fails when the model returned a check question (the runner sees it in the provider's events, because `askEvents` drops it from the tour). Before a local repo runs, the temp copy gets a `.env` with a fake `sk-ant-` key. The `fake` provider replays `test/fixtures/recordings/basic-tour.jsonl`. A run with any pass or fail check false gets a `failure` label from `classifyFailure` (`failure.ts`): `reasoning-miss` for invalid JSON or a provider error, in brute-force mode, or when every `mustHighlight` file was opened; otherwise `retrieval-miss`. The score table adds a `retrieval-miss` and a `reasoning-miss` column with the number of runs per case. The highlight, order and anchor-failure checks and the judge's highlighted code use only each step's own anchor ranges (`anchorRanges` in `src/shared/tour.ts`), never a primm target; `noCodeInNarration` also checks the primm predict and investigate prompts, and `noSecrets` also scans the target's quoted line. `--compare <a> <b>` prints each check's pass rate (or average) before, after and the change for two result files.

`--judge` (`judge.ts`) grades each run that produced a tour: `judgeRun` sends the same provider a plain request (`tools: false`) with a fixed rubric that assumes an intermediate learner, the case's intent and question, the tutor's answer and the highlighted code (both wrapped as untrusted blocks and redacted), and reads one `dimension: grade` line per dimension from the reply (not JSON, because the Claude stream parser reads a JSON line as a step). A reply that is missing a grade or has one outside 1–5 is logged with `logError` and that run stays ungraded. Grades are stored in the run's `grades` and shown as averages in the score table. `--calibrate <result> <grades>` (`calibrate.ts`) compares a human `grades.json` (`[{ case, correctness, clarity, questionQuality, intentFit }]`, `case` the 0-based index) with the judge's grades for every graded run of that case and prints, per dimension, exact matches and matches within 1.

### Model output and untrusted content

- The model answers in NDJSON: one `Step` JSON object per line, then optionally one final line `{"checkQuestion": "…", "checkConcept": "…"}`; the prompt asks for a check question only after a walkthrough of an important idea, and only when the question text says one is allowed. When a message needs no code ("I don't know", thanks, small talk), the model answers in plain sentences instead. Providers parse each complete line into a `step` event (or a `checkQuestion` event for the final line) as it streams. Before a step is validated, `withoutBadAnchors` drops anchors that fail the anchor schema and repoints the narration's anchor indexes. A line that is valid JSON but still invalid becomes a non-retryable `error` event whose `message` is the friendly `lostThread` sentence and whose `detail` is the validation error; an invalid step also sets `invalidStep: true`. On the first such event `askEvents` keeps the steps already sent and asks the provider once more with the question plus the accepted steps and the redacted validation errors, wrapped as untrusted blocks, asking it to re-emit from step N; a second failure of any kind ends the ask with the `error` event. The API providers put the first attempt's usage on that `error` event (`usage`), and `askEvents` adds it to the retry's usage in the call log and passes it to the retry as `spent`, so the retry's loop budgets (tokens and cost) count what the first attempt already used; it also passes the time the first attempt started as `startedAt`, so the 90 s time limit holds for the whole ask. The usage on any other model-line `error` event is added to the call log too. Non-JSON lines are `text` events: with no steps they become the tour's `reply`, spoken and shown as the tutor's message; next to steps they are ignored and logged. The final line may carry `scope` and `intent` together (`{"scope": "side", "intent": "debugging"}`) or either alone; it becomes a `scope` and an `intent` event. An intent outside `intents` is dropped with one `logError` line and the tour is kept; a bad scope still fails the line. The strong model infers the question's intent in the same call (the system prompt gives each intent its emphasis), so there is no extra call. `POST /api/ask` accepts an optional `intent` (`intentSchema`, `src/shared/intent.ts`): the learner's choice from the chip's menu, which the browser sends on every later ask until the learner picks Auto. `askEvents` then tells the model the chosen intent in the question and keeps the chosen intent on the tour over any intent the model reports. The pipeline builds the `Tour` from the request's question, the steps, the check question and its concept, the reply, the scope and the intent. The question policy (`src/server/teach/question-policy.ts`, one `createQuestionPolicy()` per server in `createAskHandler`, counters in memory) decides before the request: `mayAsk(frequency)` is true in teach mode on every 3rd (light), 2nd (normal) or each (frequent) eligible tour, and false while two skips in a row are backing it off; `askEvents` tells the model through `questionRules` (`prompt.ts`), which also lists the concepts already checked (`createLearnerRecord().checkedConcepts`, read through the record's write queue) as an untrusted block. After the response, `vetQuestion` drops the question unless it was allowed, the tour has steps and does not end with `scope: "side"`, and `checkConcept` names (ignoring case) an important concept of the tour's `concepts` that is not checked or reviewed; a drop is one `logError` line. A tour with steps and no `scope: "side"` in teach mode is an eligible tour: `tourEnded(kept)` advances the schedule. `skipped()` counts a skip, and a skip right after another question's skip (no other kept question between) starts a 3-tour back-off; `POST /api/skipped` calls it. Without a `questionPolicy` option a question is never kept; the eval runner passes a policy whose `mayAsk` is always true (answer mode still allows nothing), so every teach-mode eval case may keep a check question and a primm. `ClaudeHeadless` (`claude-stream.ts`) reports tool calls by their plain name (`read_file`, without the `mcp__miyagi__` prefix).
- API providers share `runAgentLoop` (`src/server/llm/agent-loop.ts`) and a neutral model interface, `AgentModel.step(messages, tools, signal) => { text, toolCalls, usage }`, with neutral `AgentMessage`s (`user`, `assistant` with tool calls, `tool` with outputs; a shared zod schema in `src/shared/agent-message.ts`, because they travel on `LLMRequest.history` and the `done` event). `runAgentLoop` returns every message of the ask, including the final answer; the API providers send this ask's part of it on `done`. The loop runs the tools directly, wraps each result with `wrapUntrusted`, and stops on 20 tool calls, 90 s, 150k tokens or $1, the same tool with the same input twice, 3 tool errors in a row, or an abort. It warns "3 steps left, wrap up." after the 17th call, and after a safety stop makes one final call with no tools asking for an honest partial answer.
- `ClaudeAPI` (`claude-api.ts`) implements `AgentModel` on `client.messages.stream(...).finalMessage()`. The system prompt is the `system` field; the first user message holds the repo context (with a cache marker) and then the first message of `request.history` or the question; the last block of the last history message carries the second cache marker. Assistant turns are sent back as the exact content blocks the API returned (thinking blocks included), kept in a module-level `WeakMap` keyed by the turn's tool calls, so turns kept in the session are sent back unchanged; a turn without an entry is sent as its text. `thinking` is not set (it cannot be disabled on Opus 5.5); `output_config.effort` is `low` for the `small` request model and `medium` otherwise. `tool_choice` is `auto`, or `none` for the final tools-off call. A refusal or `max_tokens` stop becomes a non-retryable `error` event, a 429 or 5xx a retryable one.
- `GeminiAPI` (`gemini-api.ts`) implements `AgentModel` on `client.models.generateContent`. The system prompt is `systemInstruction`; the first user message holds the repo context and the first message of `request.history` or the question as separate text parts. Assistant turns are sent back as the exact `Content` the API returned (thought signatures included), kept in a module-level `WeakMap` keyed by the turn's tool calls; a turn without an entry is sent as its text. Tool results are `functionResponse` parts with `{ output }` or `{ error }`. Tools are declared with `parametersJsonSchema`; the final tools-off call keeps them with `functionCallingConfig.mode` `NONE`. Input tokens are the prompt tokens minus cached ones, output tokens include thinking tokens, and cost is always `null`. A `MAX_TOKENS` stop or any other non-`STOP` finish becomes a non-retryable `error` event, a 429 or 5xx a retryable one.
- Every tool result shown to a model is wrapped by `wrapUntrusted(tool, text)` as `<untrusted_content tool="<tool>">…</untrusted_content>`, with a literal closing tag inside escaped as `<\/untrusted_content>`.

## The `.tutor/` folder (in the user's repo)

```
.tutor/
  .gitignore     ignores everything except itself and tours/
  tours/         saved tours: committed and shared
  private/       profile, intent, learner record, session record, call logs (never committed)
```

`askEvents` reports one `CallRecord` (`src/shared/call-log.ts`) per ask to its `callLog` writer; `/api/ask` passes `appendCallLog` (`src/server/call-log.ts`). Both it and `writeSessionRecord` write through `writePrivateFile` (`src/server/tutor-folder.ts`), which creates `.tutor/`, its `.gitignore` and `.tutor/private/`, checks `.tutor`, `.tutor/private` and the file with `lstat` and `realpath`, and then writes: `appendCallLog` appends one JSON line to `calls.jsonl`. A failed check or write logs one `Call not logged: <reason>` line and never fails the ask. `addFirstSound` rewrites the last line of `calls.jsonl` with `firstSoundMs` (through the same `writePrivateFile`; a missing log or a last line that is not a `CallRecord` logs one `First sound not logged: <reason>` line). The browser (`createFirstSound` in `src/web/first-sound.ts`) times from sending a question to the first narration audio starting and posts it only after the ask stream has ended, because the call is logged when the ask ends; the spoken acknowledgements do not count. After a `done` ask (once the `done` event is sent, so it never delays the answer), `askEvents` hands `conversation.session()` to its `saveSession` writer; `/api/ask` passes `writeSessionRecord` (`src/server/session-record.ts`), which validates it with `sessionSchema` (`src/shared/session.ts`) and replaces `.tutor/private/session.json` with `{ startedAt, summary: string | null, turns: [{ question, record }] }`: the redacted questions and one-line records of the turns the conversation still holds, plus the summary that replaced older ones. A failed check, invalid session or failed write logs one `Session not saved: <reason>` line. `CodeSource` has an optional `tutorRoot`, the folder that holds `.tutor/`: the project root for a local folder, and `~/.askmiyagi/<owner>-<repo>/` for a GitClone source (`openGitClone` creates it; the temp clone is deleted on dispose but the store stays). `cli.ts` passes `source.tutorRoot ?? source.root` to the ask, first-sound and profile handlers. The profile is `{ level, mode, frequency, goal }`: `readProfile` returns `null` for a missing file, and for an invalid one logs one line and renames it to `profile.json.corrupt`; `/api/ask` hands `askEvents` a `loadProfile` function, which it calls after the `ack` is sent so the read never delays it, and `askEvents` appends `profileContext` (the level, and the redacted goal wrapped as untrusted) to the question. In the browser, `createSetup` (`src/web/setup.svelte.ts`) asks `GET /api/profile` on load; with `null` the conversation panel asks the four questions from `src/web/profile.ts` one at a time, rendered by `SetupItems.svelte` (buttons for the first three, the question box or push-to-talk for the goal (a clicked suggestion is asked, never taken as the goal), Skip on each; a skip sets the answer to its default: intermediate, teach, normal, no goal), speaks them when voice is on (on first launch the first one waits for the first click or key press, because the browser refuses speech before then) and saves with `PUT /api/profile`. The Profile button in the panel header asks them again with the saved answers pressed. Integration and e2e tests run on a temp copy of the fixture so no `.tutor/` appears in `test/fixtures`.

## Code intelligence

`parseFile(path, source)` returns the cached `web-tree-sitter` `Tree` for the extensions in `grammarsByExtension`, or `null` when there is no parser. Trees are cached by grammar and source SHA-256. See [ADR 0001](adr/0001-parse-cache-trees.md).

`readRedactedFile(root, path)` (path guard, then redaction of the whole file) is the only way the repo map, the tools and the anchor resolver read a file (old-side anchors read the base version with `readBaseFile`, which checks the path is visible and redacts the same way), and they parse the redacted text. Redaction keeps line numbers, so tree positions match the file.

`findDefinitions` in `src/server/code/symbols.ts` is the one walker for declarations and class or interface members. `find_symbol`, the repo map and `read_file` outlines use it, and `uniqueDefinition` (one match, or a not-found or ambiguous reason listing candidates) serves both `read_file({ symbol })` and symbol anchors.

`grep` never lets ripgrep see the raw files: it streams the redacted text of the selected visible files into `rg --json -` on stdin and maps stdin line numbers back to each file. A pattern can therefore only match text the model is allowed to see.

`git` (`src/server/tools/git.ts`) runs `diff`, `show` or `log` for the model and nothing else. `parseGitArgs` (`src/shared/git-args.ts`, run by `gitInputSchema`, which hands the parsed arguments to the tool) sorts the arguments into display flags, a `-n` count, revisions and paths after `--`, and refuses every other flag (so `-c`, `--output` and `--no-index` never reach git), a revision with odd characters or a `^{`, `^@`, `^!` or `^-` suffix, and a path that is absolute, has a `..` segment (split on `/` or `\`) or starts with `:`. Each end of a revision is passed as `<end>^{commit}`, so a blob or tree hash can't be read around the file filter. Git runs through `runGit` with an argument array, `shell: false`, `core.fsmonitor=false`, `log.showSignature=false`, the diff prefixes pinned to `a/` and `b/` (`diff.noprefix` and `diff.mnemonicPrefix` off, so the risk scan can read the file headers whatever the user's git config says), the clean filters of `lfs` and of every driver the root `.gitattributes` names switched off (`filter.<name>.clean=`, `.process=`, `.required=false`; an unusual driver name is refused), `GIT_OPTIONAL_LOCKS=0`, no inherited `GIT_*` variables, `--no-ext-diff --no-textconv --no-color --no-renames --relative` and a 30 s timeout for the whole tool call (the process tree is killed), and `log` shows 50 commits unless `-n` says otherwise. Hiding works by pathspec, not by parsing output: a listing run (`--name-only -z`, with the same revisions and count) finds the changed paths, `isVisibleInDiff` picks the hidden ones, and the listing repeats with those excluded by `:(exclude,literal)<path>` until no new hidden path appears (at most 10 rounds), because leaving out a hidden-only commit lets `-n` reach an older one. The real run then uses the same excludes, and one more listing round afterwards refuses the result with "try again" if a hidden file it had not seen changed in the meantime (an edit or a new commit between the runs). So a commit that touched only hidden files does not appear in `show` or `log`, and a change with too many hidden files for the command line is refused with a hint to add paths. Output is redacted and capped at 200 lines with an `N more lines` note; output over 2 MB is cut and ends with `More lines were cut`. Redaction also catches private key blocks inside `+`/`-` diff lines.

`resolveAnchor(root, anchor, base?)` returns `Result<ResolvedAnchor>`. An anchor with `side: "old"` is resolved in the base version of its file, read by `readBaseFile(root, base, path)` (`src/server/source/diff-base.ts`: the path must pass `isVisibleInDiff`, so a file deleted since still reads; `uncommitted` reads `HEAD`, `branch` the merge base with the default branch, both with `git show --no-textconv <commit>:./<path>` so a project folder inside a larger repository works, and `snapshot` reads the copy through `readSnapshotFile`; a file with a NUL byte is refused and the text is redacted); with no `base` it fails with "An old-side anchor needs a diff base". The resolved anchor keeps the anchor's `side`. A line anchor's text matches the nearest line that is equal with whitespace collapsed, then (for text of 8 or more characters) the nearest line containing it. A symbol anchor uses `uniqueDefinition`; when that finds nothing, is ambiguous, or the file has no parser, `declarationLine` takes the first line that declares the name (a keyword such as `function` or `def`, then a method head, then `name = (`), or else mentions it outside an import; a qualified name searches after its owner's declaration. Anchors that still fail are logged as `No highlight for <file>: <reason>`. A line anchor takes the smallest syntax node spanning the line's trimmed text and climbs to the nearest `*_statement`, `*_declaration`, `*_definition` or `*_signature` node.

The side-by-side view: in `App.svelte` a `PlayerStep` carries the `base` of the diff that asked for it (`DiffRequest.base`), and `anchorTarget` hands it to `moveHighlight`, so the `Highlight` has a `base` exactly while a diff tour is on screen. `CodePane.svelte` then renders `DiffViewer.svelte` instead of `Viewer.svelte`: it loads the old version (`fetchFile(path, token, base)`: `GET /api/file?path=&side=old&base=`) and the new version (`fetchFile(path, token)`) together and shows them in a read-only `MergeView` from `@codemirror/merge` (old pane on the left, no collapsing of unchanged lines). A version that can't be read (a file added or deleted since the base) is shown empty with a status line saying why; both unreadable is an error. `onSide` in `src/web/editor.ts` gives each pane only the ranges whose `side` is its own (`new` when a range has none), and `showRanges` highlights and scrolls to the current range. The new pane keeps point-and-ask (`pickSelection`); the old pane does not. `Viewer.svelte` and `DiffViewer.svelte` share the theme, syntax colours and highlight field in `src/web/editor.ts`.

PRIMM in the browser (voice on only): `createPlayback` takes an `interlude(at, when, signal)` hook and calls it with `"before"` at the first segment of every step and `"after"` after its last one. `createPrimm` (`src/web/primm.svelte.ts`) answers it for the step that carries `primm`. Before: it shows the step's code, and the tutor says the predict prompt; the learner's next typed or spoken message (or a Skip on the chip above the composer) ends the wait instead of being asked as a question, `POST /api/predict` answers a sentence, the tutor speaks it, and then the narration plays. After: the tutor says the investigate prompt with the highlight hidden; a click in the code (`Viewer` reports the clicked line) inside the target's range is right, any other click gets "Not quite, it's here." and the target highlighted. The target's range is the one after the step's anchors in `ranges`, and nothing is investigated in a diff tour or when the target did not resolve. Each part runs once per tour (a new ask `reset`s only the parts of its own tour question, so a tour set aside for a side question does not ask again when it is restored); stopping playback ends a wait without marking it done. After the `"after"` interlude, playback reads the steps again, so a step that streamed in while the learner was investigating is still played. The modify prompt is the tour's check question, which has a Skip question button that sends `POST /api/skipped`. In text mode there is no PRIMM.

The tools share `runTool` (input validation with zod, errors as results with the root path, written with `\` or `/`, replaced by `.`) and the `ToolResult` type in `src/shared/tool-result.ts`.

## Prompt layout and caching

```
system prompt -> repo map (or whole filtered, numbered repo in brute-force mode)
  -> [cache marker] -> earlier turns (API providers: messages; ClaudeHeadless: text) -> [cache marker]
  -> question (+ selection, current step/segment, learner intent)
```

- Stable content first, so the prefix stays cacheable. The repo map is deterministic for the same file hashes.
- `ClaudeAPI` sets the cache markers explicitly; `ClaudeHeadless` relies on Claude Code's own prompt caching with the same stable order.
- Brute force vs agentic search is chosen by token count at load and re-checked as the conversation grows. The threshold is a setting tuned by evals.
- `buildRequest(root, question, bruteForceTokens, selection)` in `src/server/llm/prompt.ts` returns `{ mode, request }`: the system prompt, then the whole filtered, redacted, line-numbered repo (`=== <path> ===` headers, `12: code` lines) when it fits under the threshold (estimated as characters divided by 4; default 60,000), otherwise `buildRepoMap`. `renderPrompt(request)` joins system, context, conversation and question in that order (ClaudeHeadless); the API providers send `request.history` as messages instead.
